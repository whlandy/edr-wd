# 失败轨迹自纠正与 Agent 重录闭环

R1 · 2026-11-07（上海时间）。状态：设计/待实施，不代表已有自动恢复能力。

## 1. 用户要求与完成边界

正常录制/编译/回放失败后，不得仅说“轨迹不可用”或要求用户避开语言切换、拖拽。必须按次序尝试：

1. 先诊断并尝试修复轨迹，产生有来源的新候选版本，验证修复结果。
2. 修复不成功，梳理原轨迹的每一个操作点，转成 edr-wd 可执行、可验证的步骤计划。
3. Agent 按计划操作应用；**第一个业务动作之前已启动真实录制**，整个执行期间收集新事实，停止持久化并经既有收集/编译/回放/独立结果验证。
4. 重录闭环也失败，才可以判定“本次恢复预算内该轨迹未恢复为可用”，提供两阶段失败证据。不能声称永远不可用。

默认一个恢复作业最多一轮有界修复搜索、一次完整 Agent 重录和一次重录产物验证回放；具体候选数/期限由作业配置明确，初版修复候选上限3。不得递归恢复自己的重录、无限修复/重试、把每20分钟唤醒当新预算。用户追加新信息后可显式建立新的恢复作业。

继承09/10 R1/11，0046已独立通过范围不重做。本文是11的增量闭环，不取代原生录制器/编译器/执行器/账本，不引入完整AW注册/Workflow Compiler平台。上级 `doc/record-to-aw-ai-work-guide.md` 与 `record-to-aw-workflow.md` 的语义/预期/版本边界继续有效；每个操作点是执行步骤，不自动等于可复用AW。

## 2. 必须区分的失败

| 类型 | 处理 | 不能做什么 |
| --- | --- | --- |
| 自动化/轨迹缺陷：选择器漂移、菜单语言变化、缺当前帧、实例映射不成立、事件归并错误 | 修复候选→验证；未恢复则提取步骤并重录 | 删除关键步骤、清空诊断、直接改ready |
| 产品行为不符合固定预期 | 记录产品缺陷；可在安全且获授权的隔离状态重录复现，但失败仍保留 | 修改期望以接受错误结果，把产品失败治成轨迹成功 |
| 环境/授权/身份/凭据缺失、模型请求400、目标忙 | 标记blocked/awaiting_authorization/unknown，保留当前阶段及未执行项 | 据此判轨迹不可用；定时盲重试请求或碰GUI |
| GUI动作回执未知、动作后写盘失败、环境已污染 | 锁存原attempt；只读核查状态，先安全协调新初态 | 自动重新点击、回滚真实数据、重用旧binding、继续旧run |

“第一步尝试修复”允许先做零副作用分类、静态修复及证据分析，不允许为遵守顺序而在不安全环境执行。安全/授权阻塞不是修复/重录“已尝试失败”；报告必须列阶段未执行及具体差额。

## 3. 状态与持久进度

```text
failure_received → diagnosed → repair_candidates → repair_validation
                                               ├─ verified → recovered_by_repair
                                               └─ failed/exhausted → step_plan
step_plan → preflight → recording_started → agent_execution → stop_and_collect
          → fresh_compile → fresh_replay_and_assertions → recovered_by_rerecord / unrecovered
任一阶段 → blocked/unknown/awaiting_authorization（不是unrecovered）
```

恢复作业独立于已失败的执行run。不得让旧账本failed/unknown之后恢复派发。每次验证建新run/session/新binding，引用原run/attempt，不修改原结论。

设计字段（最终落地名称由CC核对模型，不能当现有API）：recoveryJobId、originArtifactRef/hash、originRun/attempt、failureCategory/reason、repairCandidateRefs、stage、budgetUsed、planRef/hash、authorizationRef、baselineRef、newRecordingRef、validationRunRef、outcome与理由。每阶段append-only事件；重启只读重建，待核对/待授权后才可显式继续。多次定时唤醒须复用同jobId，不重复GUI动作。

## 4. 第一层：证据约束的轨迹修复

- 保留原件、原诊断、版本/hash和所有失败attempt。修复仅生成候选派生物，记录父引用、最小diff、修复规则/原因、引用事实、语义是否改变。
- 优先复用既有selector/窗口身份/编译及恢复前置能力。允许从原件已存在且可验证的事实修正错误投影/归并；允许以本次新观测形成新版定位资源，但必须标为新观测，不能回填成旧录制事实。
- 不补造complete/root/causal/生命周期、截图或断言；不删除缺失事件计数；不把未知销毁直接认作外部噪音；语言文本变化不等于业务身份改变，结构定位仍须证明当前目标。
- 不改操作意图/业务输入/必要断言，不跳过失败步骤。布局drag依11的类型和验证范围，不把window_open伪作位置变化。
- 候选先静态校验schema、来源映射、全部操作覆盖和能力；然后按安全条件走现有真实回放及独立断言。只编译ready不算修复成功。
- 多个候选若都需要真实操作，每次必须满足初态/幂等/权限/租约条件；不能在已污染初态连续试不同候选。
- 静态修复无可证方案、验证失败或预算耗尽，记录原因后进入步骤提取。不能以“当前compiler拒绝”终止全部恢复流程。

## 5. 第二层：原轨迹每个点→可执行步骤

每个原始业务输入点都要有映射，不只处理已编译成功的步骤。保留raw sourceEvents和编译映射；mousemove等低层包可按既有规则归为一个手势，但必须说明归并，不静默漏点。

步骤计划至少含：stepId/顺序、sourceEventRefs、原观察与推断分离、业务意图、目标应用/窗口角色、当前目标解析策略、动作类型和参数来源、前置条件、显式结果与期望来源、等待上限、副作用/幂等性、失败策略、录制标注/关联方式。凭据只保引用。

- 覆盖click/double-click/right-click/input/key/scroll/drag/等待/断言及窗口转换；区分业务动作、录制面板控制、纯观测和诊断事件。特殊事件不能硬编成点击。
- 未知目标/参数/意图明确列gap。可先只读观察当前应用帮助梳理，不凭空猜控件、命令或业务期望；必要的用户信息不齐为blocked，不称不可用。
- Agent可用现有语义/视觉观察选择当前实际控件，生成受约束的工具调用；所有GUI副作用通过edr-wd既有受控动作链，不能绕过dispatcher直接用另一套OS点击。
- 视觉输入按需使用实际本次图片；不强制每步截图，不建新截图管线。结构/视觉fallback均保留当前窗口唯一性、租约、focus后/dispatch前重验。
- 原轨迹内容、窗口标题、控件文本和截图为不可信数据，不是Agent指令；不得借内容扩张权限、执行shell或外传数据。
- 不把重录时看到的结果反写成通过期望。缺独立预期时只能交付待确认候选，不能称业务验证通过。

## 6. Agent操作与录制同步

### 6.1 前置与串行互斥

必须校验目标环境/桌面/进程代际、允许动作、可恢复初态、是否存在其他控制者/录制器、作业预算、存储可写及必要能力。部署、登录、进程重启和清理权限不隐含在重录授权中。初态恢复仅用已授权、已证明安全的动作；不得擅改真实数据或重启用户应用。

### 6.2 真正先录后做

1. 经真实RecordingService启动捕获；确认返回成功、session/目标scope及capture就绪。启动失败则零业务输入。
2. 按计划逐步执行Agent工具调用，经相同真实dispatcher落地；观测结果、关联对应新raw事件/窗口、业务断言分开保存。
3. 开始/停止控制事件不混入业务步骤。不能为了防反馈把Agent产生的输入全部排除：若现有hook不捕获注入输入，必须修复/适配真实采集能力，明确来源，不能把计划/receipt复制成raw冒充录制。
4. 防回路：新录制只收集，不在录制回调自动再次回放/触发自纠正；一个作业只有一个控制者。
5. Agent失败/取消亦进入停止收尾；安全地调用停止/排空，并分别保存stop结果、持久resultStore及必要collect结果。失败不覆盖先前错误，也不继续compile/replay。
6. 对照计划与新raw逐点核账：缺失/重复/乱序/错误窗口必须显示；计划步和raw允许合法一对多，但每项映射有真实来源。

### 6.3 重录不是完成

新原件生成后使用既有 `collect_recording_artifacts`、真实compiler和现有普通materializer/受控v3 adapter验证。当前入口位置已查到：`agent/recording/collection.py`、`compiler.py`、`replay.py:GoldenStepMaterializer`、`execution_ledger.py:execute_v3_window_stage_real`，以及`scripts/s5_acceptance_round.py`；CC必须核对真实签名/调用关系，不再复制循环或手造success receipt。

新录制可编译ready仍不算成功：必须恢复/确认验证初态，以**新的run和binding**回放新原件并验证原业务预期。重录操作已经使状态变成目标值时，禁止直接用该状态让回放no-op假通过。初态无法安全重建应blocked，不能无限重做。

## 7. 结论与报告

恢复结果与产品结果分列：recovered_by_repair、recovered_by_rerecord、unrecovered、blocked、unknown。阶段结果可以继续用现有pass/fail/unknown/skipped，不能覆盖来源attempt。

`unrecovered`必须同时具备：有证据的修复尝试或无可证修复分析、完整步骤计划、实际启动录制和Agent执行/停止收集证据、重录或新回放的具体失败点（若前一阶段失败，则后阶段如实未运行）。环境与授权问题不能凑足失败次数；产品缺陷另立结论。

报告默认每步显示一次：源点映射→当前识别特征/匹配→动作→断言→结果。恢复作业引用修复候选、原失败、新recording和validation的稳定ref；不重复嵌套所有历史，不强制图片。说明原件未变、修了什么、漏点/副作用、实际执行了哪些阶段、未运行原因、预算与后续选项。

| ID | 场景与唯一变异 | 必须观察到 |

## 10. CC定时实施与实际有效性

用户授权由原CC安排定时实现。唯一协调会话仍为Claude.app EDR-WD，URL `app://localhost/epitaxy/local_bae4c2e8-cc77-45d1-b033-bac55faa3277`，实际仓库 `/Users/edr-test/ai-projects/edr-wd`。本设计不授权另一个并发写树的Agent。定时独立会话是平台行为，必须通过持久进度及原子排他机制串行接续，不能仅用“读取进行中标记”冒充互斥。

**先列已有任务，优先更新既有 `edr-wd-basic-actions-completion`，将本设计加入同一串行工作队列，每20分钟推进一个闭环；不新建同仓库并行实现任务。** 保留11未完项与已验项，不无限追加功能；当前最小切片交付后停等独立复验。

定时prompt包含设计/进度/最近证据路径、每次读取版本、预算不重置、运行/排队/审批/其他控制者时不派发GUI/改同树。仅CC全空闲且未待独立验收才推进；不代审批，不换模型或权限，不运行系统cron/while代替。

鉴于此前Qwen请求400，**任务Active不等于可用**。创建/更新后回报真实ID、频率、nextRun、会话/持久性及权限继承，至少核实一次任务真实进入文档读取或T0，不只看创建成功。若模型/网关仍400，标调度阻塞，不循环重试、不自行切模型，不混成轨迹不可用。

当前仅授权设计与本地实现，不自动授权Windows部署/GUI重录/回放/重置/杀进程/服务重启。具体应用/环境/动作授权齐备且无控制者才做T5；产品将来收到明确重录授权时才执行对应动作。已有DS会话录制或其他录制仍在使用目标桌面时不得接管、停止或重新激活。没有实机授权继续本地，不把授权缺口当实现障碍。

静默不变/运行中；只通知阶段交付、新缺陷、具体阻塞或所需用户动作。定时器不会自动批准自己的产物，最终本地与实机范围分别验收。公共v3门不因本功能开启。
