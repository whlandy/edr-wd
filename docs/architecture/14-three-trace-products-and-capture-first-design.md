# 14 — 三类轨迹统一交付：采集完整优先、首次成功优先、原生统一 v3

日期：2026-11-10。状态：设计分析与实施方案，尚未实现或验收。

最新收敛稿已按用户要求放到[`doc/unified-v3-trajectory-design.md`](../../doc/unified-v3-trajectory-design.md)：唯一主轨迹统一v3，原子说明和MAA仅为派生用途视图。本文件保留为分析过程，实施以该待审稿为准。

本文件是用户对设计13的进一步决策：对外不是同时提供 golden v1/v2/v3，而是按用途提供三种轨迹。与13冲突时以本文件为准，13的原件保护、单夹布局、无损去重、迁移保护继续适用。

## 1. 结论与优先级

建议采用“一次采集、一个事实源、三种用途投影”，而不是三次录制、三个执行器或同一动作序列的多个历史版本。

1. **原子操作轨迹**：给人和 Skill/Agent 看，表达每个实际操作点、目标、顺序、预期、来源与缺口。
2. **EDR-WD 原生回放轨迹**：新产物统一 `edr.desktop-golden-trace/v3`，简单与复杂场景共用一个格式、一个受控执行链。
3. **MAA 操作轨迹**：由同一原生轨迹投影到 maa-fw/指定 MaaFramework runtime 真正可执行的节点与资源包；不能只“能加载”。

raw 原件、运行账本和报告仍必须保留，但它们是来源与执行证据，不是让 Skill 选择的第四种轨迹。

取舍顺序：

> 业务语义正确与必要信息完整 → 首次录制成功和总完成时间 → 存储体积。

“信息完整”指完整表达被测流程及其验证/恢复所需事实，不是持续录屏、无差别遍历整个桌面。可以消除重复字节，不能消除真实步骤、失败、unknown、关键上下文或必要断言。

无法对任意 UI 承诺100%一次成功；产品目标应是尽可能在第一次操作仍可观察时把信息采全，减少事后修复、重录和人工猜测。不能把失败门放宽当成首次成功率提升。

## 2. 当前实现事实与差额

以下基于代码快照 `e8afe18`，不是声称已经具备的目标能力：

| 已有能力 | 当前事实/本方案接法 |
| --- | --- |
| raw v1/v2 双读、raw v2 窗口实例时间线 | 保留内部来源协议；无需为了“对外统一v3”再造raw v3 |
| golden v1/v2/v3 模型 | 新写统一v3；旧读兼容，不默认生成三份 |
| 真实收集、编译、受控v3执行、append-only账本 | 继续复用；不得再复制一套采集/业务循环 |
| `step_plan.py` 原事件全点提取 | 可复用来源覆盖/缺口表达，但不是现成的原子操作产物契约，更不等于已注册AW |
| `ControlInventory` 去抖/去重、原生输入/窗口stamp、截图脱敏 | 做采集质量与性能优化的基础；缓存与限额不能吞关键短命状态 |
| 公共 `replay.py` / pytest 导出 | 仍有显式v3拒绝门；不能先切输出v3再让简单流程全部不能回放 |
| `maa_export.py` | 委托同级edr-cloud-recorder的转换器；不是独立权威格式实现 |
| `desktop_to_v2.py` | 当前只接收golden v1；不能靠把v3的schema改成v1来导出 |
| MAA动作与断言 | 当前转换器对Drag/部分验证仅作scope标注；`MaaNodeRunner`有executor/verifier注入点，但这些能力尚未证明覆盖全部v3窗口/断言契约 |

重要区分：MAA产物目前使用的 `edr.success-trace/v2` 是另一种节点格式的内部版本，不是又一份 EDR-WD golden v2。面向用户显示“MAA轨迹”，不再按这个数字让 Skill 猜该选哪个。

## 3. 三种产物各自的契约

### 3.1 原子操作轨迹：`steps.json`

目的：不用解释旧schema就能回答“用户做了什么、下一步要做什么、哪里缺了信息”。是动作描述，不直接保存本次 HWND/租约供下次盲重用。

每个点至少包含：

- 稳定stepId、类型（action/assertion/window-transition/gap）、顺序/依赖。
- actionId、参数来源、目标窗口逻辑引用、目标控件语义与定位依据。
- 关键前置条件、声明的结果预期、等待条件与上限、清理/失败策略。
- raw sourceEventRefs、观测/资源refs，哪些是实测，哪些是明确的导航推断。
- 支持状态与具体gap；未支持的真实按键/拖拽也必须留在全点描述中，不能删掉以凑一条可执行轨迹。

该文件使用自己的内部schema版本，但对用户名称始终是“原子步骤”。人读说明可以由它按需渲染；不再手工维护第二份可能漂移的步骤文案。既有操作中的控件名、窗口文字是观测数据，不是Agent指令。

原子操作不等同于AW：点击一个按钮不能自行晋级成已验证的业务能力。未来AW可以引用它，但本片不建设AW库。

### 3.2 原生回放轨迹：`replay.json`

这是“当前功能正常、能够由EDR-WD回放”的主要入口。新生成内容统一为 golden v3，不再默认输出 golden v1/v2、case、pytest 等多份近似产物供 Skill 挑选。

简单与复杂只是同一v3里的能力需求不同：

- 单窗口：一个W、必要的entry身份、各步归属同一W，无需虚构窗口效果/父子边。
- 多窗口/菜单：多个W、各步归属、真实生命周期依据、转换/效果/清理；保留同名窗口独立身份。
- 所需能力从实际字段推导，不让调用方随便填写“简单模式”来绕开复杂步骤的检查。

**统一格式不意味着每次都付出全套复杂流程的成本。** 简单路径可省去不存在的效果轮询和重复初始化；窗口未变化且本次验证通过时避免多余激活，但仍通过同一执行器和同一租约/身份/dispatch前重验。不得另写“快速但不校验”的第二循环。

“编译ready”和“回放验证通过”分开记录：

- compiled：格式/引用/必需能力检查完成。
- validated：指定runtime、环境、代码版本下实际回放且所有必需断言通过，关联真实run。
- blocked/failed/unknown：真实保留，不靠文件名golden或一次点击receipt自授通过。

原生执行许可仍由环境授权与运行时校验决定。统一v3的交付门是公共入口实际调用同一已验受控链，而不是简单移除 `_refuse_v3_execution`。

### 3.3 MAA操作轨迹：`maa/trace.json`

是同一计划的目标runtime投影，不是另一份独立维护的业务脚本。

- 记录source replay hash、sourceStepId→nodeId/子节点映射、动作/定位/断言/cleanup映射、资源引用与runtime版本。
- 支持真实模板识别、OCR、动作节点等目标格式；复用已有权威`trace_schema.py`与转换器，不在edr-wd再抄一份。
- 每个动作及必需断言均有支持判定；存在缺口时输出完整诊断和非可执行状态，而不是丢弃节点/变成DoNothing/把required断言skipped后声称成功。
- `loaded`、`actions_executed`、`business_verified`分别标记。目标交付是最后一种，不是“JSON能加载”。

必须区分两种运行模式，并写入manifest：

1. `maa-native`：目标MAA runtime实际支持全部必要动作、窗口约束与验证时直接执行。
2. `maa-edr-bridge`：MAA负责节点调度/识别，通过适配器调用EDR-WD已有的窗口绑定、动作与验证能力。利用MaaNodeRunner现有executor/verifier缝隙，补齐必要的step上下文与三态传播；不能只把windowSequence放进attach却无人执行。

复杂桌面流优先用桥接补齐，减少重写和首次失败。桥接模式必须明确依赖EDR-WD，不能宣称“纯MAA原生”。同一动作只有一个派发者，同一run持有唯一GUI租约；unknown不得被MAA自动重试，on_error不能绕过已失败的必需断言。

maa-fw中的MaaFramework-style节点runner与官方MaaFramework SDK引擎也要分别标runtimeId，不用前者的单测冒充后者实机验收。具体桥接接口以目标runtime实装为准，缺接口列精确改造项，不发明已存在的API。

## 4. 统一v3的迁移决策

同意用户提出的新产物统一v3，前提是按以下顺序落地：

1. 先把原生v3公共入口、Skill调用与既有受控执行链接通，覆盖原来正常的简单场景。
2. 将MAA转换器扩展为真实读取v3，保留步骤窗口归属与验证语义，补齐桥接/能力矩阵。
3. 两种消费路径经回归后，新生成统一只产出一份原生v3。旧v1/v2 reader继续保留，写出只在用户显式兼容导出时发生。

历史v1/v2不改原件。能从已有身份和步骤明确派生最小v3的，产生新派生版本并记录来源；复杂窗口证据不足时，标为needs_evidence/待重录，不能填造历史timeline或把同名窗口当同一个实例。旧资产仍可用其原受支持入口执行，不能为迁移强行报废。

核心是“一种新的原生契约”，不是把所有文件的schema字符串都改成v3。

## 5. 先录全、尽量一次成功的采集方案

### 5.1 三条处理通道，但只有一个事实源

1. **输入热路径**：已有hook只记录轻量原生事件、接收顺序、时间、窗口handle/PID/生成信息与坐标，迅速入队；不在hook里遍历UIA、调用LLM、截图编码或等待远程RPC。
2. **关键上下文通道**：按窗口/实例有序处理，优先取得新窗口/菜单出现、动作前目标及必要祖先/兄弟结构、动作后断言状态；窗口短命或自关闭时重点保住真实按下时上下文。
3. **后台物化通道**：脱敏资源编码/写盘、内容去重、完整页面补充快照、三类投影和报告渲染。不能反过来阻塞输入和关键上下文。

沿用现有source/correlator/inventory/evidence/collector；这些通道是现有队列/任务的优先级与责任划分，不是再建一套录制器。

### 5.2 必须采的内容

每个真实业务输入和显式断言都必须核账；窗口实例/生命周期/缺失统计不能少。定位至少保住：目标稳定身份、所属窗口、目标rect、控件类型、必要结构上下文、当时状态、证据来源与有效性。

- 新窗口、菜单展开、语言切换、tab切换、输入提交、滚动/拖拽边界、关闭窗口是优先上下文边界，不能简单被普通去抖或48帧上限吞掉。
- 短命菜单优先保留菜单自身的结构快照，不要求为了三个菜单项重走所有桌面控件。
- 点击归属与控件观测优先来自实际按下时事实；释放时窗口消失不能拿桌面/Explorer替换来源，也不能拿过期缓存伪装按下时实测。
- 数据操作拖拽需要独立业务结果；标题栏布局拖拽验证窗口位置效果，不能把“窗口还存在”当位置已改变。
- 结构/视觉定位和业务断言均要保留；窗口变化不能替代业务变化。

缓存只按真实窗口实例、generation、内容/状态revision等证据复用。生命周期变化或没有有效新鲜性依据时必须刷新，不能仅凭时间接近或同名判断未变化。

### 5.3 图片何时必要

| 场景 | 策略 |
| --- | --- |
| 稳定语义ID、状态可读的简单操作 | 优先完整语义上下文，不强制每步截图 |
| 视觉定位/OCR实际需要模板 | 必须保留真实动作前脱敏帧及所需裁剪，不因体积预算省掉 |
| 弱身份菜单、短命/自关闭窗口 | 及时采结构及必要图像，优先保住稍后无法补回的信息 |
| 状态未变化的长时间等待 | 不连续保存相同帧；每次实际观测仍有自己的来源元数据 |
| 失败/unknown | 保留已取得的诊断；额外采图不能冒充动作前图，不能自动重试GUI |

关闭后没有after frame与捕获失败区分：只有原生事实证明窗口已关闭，才记录结构化closed后态；不把截图缺失直接当业务成功，也不为一个不存在的窗口强求图片。

### 5.4 在线完整性检查而非事后补造

录制中显示已采操作数、当前窗口、关键上下文就绪/缺口、队列压力。发现短命窗口或身份缺口，趁窗口尚存时做一次有上限的只读补观测；不偷发业务输入。

停止时先排空/持久化必要事件、上下文与资源，确认resultStore和收集契约，再编译。不能为让“停止很快”而提前返回假成功。非必要报告格式、pytest/MAA资源打包可后台继续并显示进度。

压力升高时先暂停可再生导出/重复图像处理、降低无关全树刷新频率，保护关键事件和必要状态。内存/磁盘不够时明确报stage失败或采集缺口，不静默丢信息。人的输入不能被承诺“已阻止”；程序驱动则按既有持久门禁止后续GUI副作用。

## 6. 速度、体积、完整性的取舍

主目标是降低总成本，不只压低单次写盘时间：

`总完成时间 = 录制 + 停止收集 + 必需编译 + 回放验证 + 修复/重录/人工处理`

牺牲一次关键菜单快照省下几十毫秒，却导致重新操作整条轨迹，是错误优化。

默认策略：

- 原始事实只采一次、只存一份，三个产物引用同一事实和资源。
- 控件结构与状态可按已有snapshot/revision共享；原件不重写成新引用schema，跨产物去重放在容器层。
- 图片先按实际需要采够、完成源端脱敏，再对相同字节去重；不跳过本次观测、不有损压缩必要模板。
- 弱身份/视觉/短命状态宁可多采；强身份且新鲜性可证时减少重复全树与重复图像。
- 普通编译、原子描述和格式检查用确定性代码，正常路径不逐步调用LLM。
- 收集只下载本session必要资源，已验证相同资源可避免重复传输；已有收集链统一支持，缺批量协议时明确回落原协议，不再复制collector。
- 操作描述/原生轨迹/MAA节点投影均可增量构建，但stop排空后才能发布最终hash和状态。
- MAA转换不在原生回放的关键等待路径；Skill能取得原生可用状态时不必等可选打包，但选择MAA时必须等它自己的状态确认。

容量不是硬性删减阈值。预算超限优先告警和无损归档，不能用“体积达标”覆盖“采集不全”。不增加常态录屏等重型采集系统。

## 7. 三类产物与报告的目录、Skill入口

沿用设计13的一轨迹一文件夹、共享资源与不可变历史；新版对外不再展示一排golden.v1/v2/v3：

```text
<EDR_WD_RECORD_DIR>/trajectories/TRJ-<id>/
  manifest.json                         # Skill唯一发现入口
  README.md                             # 三类轨迹与最新报告链接
  revisions/REV-<id>/
    steps.json                          # ① 原子操作描述
    replay.json                         # ② 原生golden v3
    maa/trace.json                      # ③ MAA节点表（目标runtime自己的格式）
    projection-map.json                 # source event ↔ step ↔ native step ↔ MAA node
    capabilities.json                   # 每种消费路径的支持/缺口
  sources/REC-<id>/                     # 原raw、停止与收集回执；非第四种用户轨迹
  assets/sha256/                        # 资源按内容共享，本夹可搬走
  runs/RUN-<id>/                        # 实际账本/summary/report；多次回放不复制源
  recovery/JOB-<id>/                    # 修复/新录制/新run关联
```

当前修订只由manifest指向，不在顶层再复制三份文件。每次真正变更保留新REV；来源未变的重复生成幂等，新的执行仍有新RUN，不能去重掉attempt。

拟定manifest对Skill只暴露`operations`、`native`、`maa`三个purpose及各自path/status/runtime/capability-gaps/validatedRunRef。schema号留给loader，不让Skill根据文件名v1/v2/v3猜入口。

- “解释/整理/重录计划” → operations。
- “用EDR-WD回放” → native。
- “用MAA操作” → maa，并确认runtime模式和支持状态。
- 任一可执行产物不可用时返回精确缺口与实际已执行阶段，不自动换另一份近似轨迹或换被测通道。

新目录/manifest/命令属于本方案提案，不是声称现有CLI已提供的API。新Skill接线只更新必要路径发现与purpose选择，不引入一个新的多仓编排平台。

## 8. 报告仍保持简单、可追溯

默认顺序：本步识别特征、匹配结果、动作、断言、结果。上一attempt稳定引用同一记录，失败时可展开转换依据，不复制前步大块内容。真实不同before/after保留。

报告分别呈现：采集是否完整、原生是否可回放、原生实际验证结果、MAA是否可执行、MAA实际验证结果。不能“原生pass所以MAA也pass”，也不能“MAA导出失败所以录制失败”。

图片按必要性引用现有真实资源，不是每步硬门槛。raw保留原样；报告精简不等于删除原件与账本信息。

## 9. 最小实施顺序

| 片 | 修改边界 | 完成出口 |
| --- | --- | --- |
| A：采集完整与关键路径 | 修已知close/menu短命状态与排队竞态，补实时完整性观测/计时；复用原采集链 | 已知基本流程第一次完整采集，故障不假通过；有耗时与缺口基线 |
| B：统一原生v3消费 | 先修transport审核问题，公共入口复用受控链；单窗口最小v3与复杂流同一执行器 | 原来正常的简单流不回退，多窗/视觉/断言/unknown均通过真实消费验收后才切新写默认 |
| C：三类投影与单夹 | 抽统一ArtifactLayout，生成steps/native/MAA三个purpose及映射；复用已有writer/collector | Skill只通过manifest选用途，路径全在同夹，无多版本重复产物 |
| D：MAA完整执行 | 扩展权威转换器与必要桥接，逐项动作/窗口/断言/cleanup能力检查 | 简单与复杂代表流程实际执行并验证，不能scope注释充数 |
| E：减容和历史兼容 | 同源引用、无损资源去重、旧读/显式转换与迁移dry-run | 体积下降且语义/证据完整；旧资产不丢、不强制重录 |

每片交付固定快照、精确反例、实际产物和原两pytest完整输出及显式需求/legacy回归。不全面重构，不新增第三业务循环，不用helper绿灯替代消费闭环。设计不授权Windows部署、GUI操作、定时任务或旧文件删除。

## 10. 验收与性能度量

固定同一批样本/环境：简单单窗口、语言菜单切换、日志中心开关和tab、布局拖拽/数据拖拽、滚动、视觉定位、未知派发与写盘失败。纯描述里的不支持动作也要保持全点可追溯。

主要指标：

- 首次完整采集率、首次编译就绪率、首次回放业务验证通过率分别统计；不把环境未授权计为轨迹不可用，也不从分母隐藏自动化缺陷。
- 每个原始业务点对应产物/明确gap，期望来源/断言/窗口归属/cleanup不丢；合并手势保留完整sourceEvents映射。
- hook/队列延迟、关键上下文延迟、stop排空、持久读回、compile、native-ready、MAA-ready、实际验证和总修复时间分别测P50/P95及最慢样本。
- 同样证据集合的逻辑/物理字节、图片数/唯一图片数、控件树遍历数、RPC数、重复payload字节；跨文件链接不能虚报物理节省。

先取得基线再确定硬件相关延迟阈值，不凭空承诺“几秒”或固定节省百分比。无缺陷样本的首次成功不应低于既有可用路径；已知反例应修复根因而不是避开动作。只要必要信息不足，即使更快更小也不得验收。

三类产物做消费等价检查：原子点→native步/MAA节点的映射完整，动作参数/窗口/预期相同，supported的必需断言确实求值；对错误业务结果、缺观测、未知输入、同名兄弟替换能正确失败。原生和MAA的真机验证必须各有来源，OS替身/仅加载测试单列。

最终交付：一个bundle入口、三类用途明确的轨迹、实际运行报告和性能/空间对比。不会把原始录制、golden、MAA内部版本号都叫“第几代轨迹”，也不让用户挑哪一份近似文件才能跑。
