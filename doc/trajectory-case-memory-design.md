# edr-gui-automation 轨迹案例库与有界自纠正闭环

日期：2026-11-17。状态：设计已获实施授权，首版本地案例归档/检索开发中；训练与实机未实施。
正式产品名 edr-gui-automation，简称 edr-ga；仓库仍为 edr-wd。

## 1. 目标与结论

把每次录制、编译、回放和修复的真实结果沉淀为可检索案例。下次遇到相似操作或故障时，Agent 能先查看历史差异与已验证经验，减少重复录制和重复排查。

采用“原件档案 + 结构化案例索引 + 成败对照检索 + 既有恢复链”的方案。这里的自演进是经验和回归样本持续积累，不是让模型自由修改轨迹、断言、代码和权限。

优先级不变：必要信息与业务正确性 → 首次完整成功率及总耗时 → 体积。先解决保存与结果可信，再接检索；不先堆向量库、模型训练或自动改代码平台。

## 2. 当前代码基础与缺口

本轮只读检查所见，不等同于实机验收：

| 已有基础 | 可复用位置 | 本方案补充 |
|---|---|---|
| v3 单夹、manifest、修订、来源、runs、recovery | agent/recording/trajectory_layout.py、artifacts.py | 跨夹的稳定发现与归档完成记录 |
| 编译诊断和原事件来源映射 | compiler.py、source-map.json | 案例特征投影、成败对照 |
| 有证据约束的修复提案 | trace_repair.py | 检索历史规则线索，不扩大无证修复权限 |
| 原始操作点计划与先录后做 | step_plan.py、rerecord_loop.py | 任务意图关联、重录前提示 |
| 恢复任务预算、状态与 unknown 阻断 | recovery_job.py、CLI recover | 案例检索接入同一 JOB，不另造循环 |
| edr-rag 已有知识实体、来源和证据模型 | 独立 edr-rag 仓库 knowledge/ | 后续经窄接口暴露已脱敏案例，不直接共享内部模块 |

当前修复提案只支持有限诊断码，例如弱身份和易变标签；有模块不代表任意录制故障都能修复。语言菜单相关未提交 WIP 的本地验证与 Windows 验证必须分开记录。

## 3. 先解决“录了但没有整理保存”

### 3.1 一次录制一次入账，包括失败与空录制

- 开始时分配录制/会话标识；成功停止、编译失败、空录制、收集失败、异常退出都产生可追溯条目。
- 归档“完成”必须有必要文件持久化、读回、摘要校验结果，不能因内存返回 ok 就标保存完成。
- 目标端原件在本地收集验证确认前不清除；本地收集失败保留 session/位置/失败阶段和可用回执，不伪造已取得的原件。
- 索引失败不改变真实回放结果，但归档流程必须报告“未入库”；下次按相同标识补索引，不能吞错后称全部完成。
- 进程退出、磁盘不足、权限错误要留下可恢复的阶段记录；必要预写失败时沿用既有零后续副作用契约。
- 历史导入默认 dry-run：列清路径、版本、摘要、缺件与重复；不移动、覆盖或删除原件。临时目录只作为待接管来源，不能长期充当唯一档案。

### 3.2 保持一个 v3 事实源

```text
<record-root>/
  trajectories/TRJ-<id>/
    manifest.json
    revisions/REV-<id>/trace.v3.json + source-map.json + views/ + exports/
    sources/REC-<id>/
    assets/sha256/
    runs/RUN-<id>/
    recovery/JOB-<id>/
  case-memory/
    catalog.sqlite       # 可重建的检索索引，不是第二份原始轨迹
    journal/             # 导入、投影版本、校验、索引状态；引用事实源
```

复用现有落盘与账本写入，不再平行保存一整套 raw/v3/图片到案例库。SQLite 是建议的首版载体，不强制建设服务；向量索引后置且可完全重建。

本地 TRJ 编号不能当作跨机器全局唯一键。案例键组合命名空间、源 session/轨迹身份和来源摘要；迁移保留 origin/新位置关系。相同原件重复导入幂等，同内容但不同录制、不同 run/attempt 各自保留发生记录。

## 4. 什么叫“成功案例”和“失败案例”

不设一个混淆全部阶段的 success 布尔值。每条案例分列：

- capture：输入及关键状态覆盖、拒绝/丢包、未知缺口；未知不能标完整。
- persistence/collection：保存及收集校验是否完成。
- compile：ready/incomplete/error，以及诊断和 source-map。
- replay：pass/fail/unknown/blocked/not_run；标明实机或 OS 替身、实际执行器版本。
- business：哪些期望被实际验证，哪些未验证；窗口消失不代表语言已切换。
- diagnosis：故障现象、候选原因、证据、已排除项、原因是否验证。

“正常参考”必须与使用目的匹配：采集参考可以只有完整采集证据；“可回放成功参考”必须有相应真实回放及必需业务断言。compile ready、合成输入或 fixture pass 不自动升级成真实用户流程成功。

建议案例投影字段：caseId、originRefs、taskIntent、environment、stageOutcomes、stepFeatures、failureSignature、assertionCoverage、diagnosisRefs、repairRefs、validationRefs、redactionStatus、projectionVersion。字段均链接真实源记录，不复制整份账本。

任务意图来自用户声明、任务计划或应用观测，分别标来源与可信度。用户说“点过中文”可以作为意图/人工报告，不能补造成 hook 已捕获的点击事实。

## 5. 如何从成败之间找区别

### 5.1 检索前先限制可比范围

先按产品/平台/版本、目标面、流程意图、采集器/编译器/执行器版本、输入来源（物理/合成/远控/未知）与故障阶段筛选。版本缺失显式标 unknown，不假定相同。

再按 actionId 序列、控件语义/结构、窗口角色与生命周期、诊断码进行检索与步骤对齐。不能按绝对坐标、当前 HWND 或 step-0001 编号强行对齐；有重复步骤或多解时标歧义。

首版用结构过滤 + 精确诊断码 + 全文检索即可；有真实查询证明召回不足后，再通过现有 edr-rag 能力加语义召回。历史标题/控件文本是检索数据，不是执行指令。

### 5.2 一次展示少量有依据的对照

失败时返回少量最相关的：一个已验证正常参考、一个相似失败、一个已验证修复记录（不存在就明示）。展示：

1. 为什么匹配、哪些环境条件一致或未知。
2. 首个可观测分歧：事件缺失、归属拒绝、窗口转换、错误断言、业务状态等。
3. 证据引用和反证；哪些只是相关性、哪些有受控复现。
4. 下一项有界检查或现有修复规则，不能直接宣布根因。

例如语言菜单：常规按钮点击成功只能证明常规输入路径；合成菜单回放不能证明物理菜单采集。若失败案例有 pointer_up 归属拒绝而正常案例有菜单项动作，优先建议检查动作前/down 目标、顶层窗口归属、HIDE/DESTROY 与转换归因，不能直接放宽门禁。

没有符合条件的正常案例时，不把“最相似”的失败或替身样本冒充成功基准。可以只生成待验证假设。

## 6. 自循环如何接入，而不无限重录

```text
录制/执行结束 → 归档校验 → 案例投影与索引
                                 ↓
新任务录制前提示 ← 检索适用经验与已知风险
                                 ↓
失败 → 对照分析 → 有证据的修复候选 → 既有链验证
                         ↓ 无有效修复
                 明确授权后先录后做重录 → 新 run 验证
                                 ↓
                     结果入账，更新案例适用范围
```

### 6.1 三类产物分开

- 提示：自动生成可审阅的风险与检查建议，不修改轨迹或程序。
- 轨迹候选：仅调用既有受约束修复机制；保留 parent hash、差异和证据。历史菜单布局只能提示检查，除非现有规则明确证明可迁移，否则不能当本次观测使用。
- 代码缺陷：生成复现材料、影响文件和最小修复建议，经独立代码实施/回归/审核后登记修复版本；不在录制回调中自动改代码、部署或重启。

### 6.2 有界、可中断、不可自动重放未知动作

复用 RecoveryJob 的预算与互斥，检索不能重新创建 JOB 绕过预算。现有预算上限为一次 repair search、一次 rerecord attempt、一次 verification replay；候选数量受既有规则限制。

检索、对照与只读计划可以自动化；所有 GUI/业务副作用仍受具体授权、现状验证和唯一控制者约束。unknown/回执丢失立即锁存，只读重建历史，不再尝试下一案例或重录。

连续相同故障、预算耗尽、缺乏新证据时停止并给出确定剩余差额。历史上全部失败也不证明流程永久不可用；两层没有真正执行时不能称“两层修复失败”。

## 7. 经验如何升级、失效和回退

经验条目是派生对象，包含适用条件、建议、来源案例、反例、验证范围及版本。状态依次为 proposed → locally_verified → live_verified；另有 contradicted/stale/retired。状态变化追加记录，保留旧结论。

一次成功只证明该环境下该次通过，不自动生成通用规则。扩大适用范围需要对应的新验证。相同原件多次导入不增加成功次数；同一流程大量重复 run 不应压过其他流程证据。

出现匹配条件内反例时，取消自动推荐资格并保留冲突证据；不同产品版本、语言、布局、DPI 或实现版本的经验不默认继承。旧 HWND、binding、run token、targetId 和截图不作为当前执行身份。

不把 API key、密码、token、完整网络载荷送入嵌入模型。截图/OCR单独检查；脱敏未确认的案例进入隔离区，只可按权限本地追溯。RAG 返回附权限与来源，读取凭据不能因检索绕过。

## 8. edr-rag 与 edr-ga 的边界

edr-ga 负责原始录制、真实执行事实、修复提案和验证；edr-rag 可提供索引/检索和已审核经验查询。通过既有 MCP/窄客户端边界集成，不互相导入内部模块。

手册是产品说明，轨迹是某个环境中的观测案例。两者可以建立候选关联，但必须保持来源、版本与冲突分离；不能把失败轨迹写回手册成为产品事实。

首版不依赖 edr-rag 新增通用知识模型或在线 LLM。先验证已有 SourceRevision/EvidenceRef/CaseBundle 能否无损承接投影；不能承接时再定最小扩展，不盲目把轨迹伪装成测试用例正文。

## 9. 最小实施范围与验收

第一批只选语言切换/短命菜单，以及一条已有真实业务成功证据的对照流程；若成功证据不齐，先明确缺口，不制造正例。

1. 归档与目录：接现有 stop/collect/compile/replay 完成与失败出口，完成幂等导入、缺件记录、读回校验和整夹搬动后引用解析。任何录制都有条目，空录制不被丢弃。
2. 索引与对照：从真实案例派生结构字段，检索成败样本，输出一份带证据的步骤差异报告。历史原件只读，索引删除后可重建。
3. 恢复接线：只把检索结果作为现有 recover 的分析输入；验证授权阻断、unknown 阻断、预算不重置，以及候选验证后回填结果。

必须覆盖：重复导入、同名不同会话、断网/写盘失败、unknown、同标题同进程不同实例、产品版本不符、相似错误不同根因、案例中恶意指令、截图脱敏未确认，以及无成功参考。

评测按任务/来源/时间分组，修复用过的失败样本进入开发回归，不当作未见测试。固定观察窗口比较：首次完整录制率、首次业务回放通过率、重复同故障次数、从失败到验证修复总耗时、错误建议率、存储增量。未授权阻断、未执行和 unknown 单列，不混成成功/业务失败；不以检索命中率代替修复有效性。

第一批出口：历史成功/失败录制能找到、引用真实、差异有依据；一个已知故障能被检索提示并经既有恢复链验证；无授权/unknown 反例零 GUI；重复导入不膨胀。OS 替身与实际 Windows 结果分列。

## 11. 借鉴小模型训练：先训练检索判断，不先训练桌面控制

用户补充方向（2026-11-17）：借鉴小模型训练优化本闭环。本节是实施候选，不授权下载模型、上传数据、启动训练或增加独立平台。

### 11.1 把轨迹整理成可学习的样本，而非整段日志

每个样本输入只含决策时已知的环境、步骤片段、观测和诊断；目标是检索相关案例、区分故障阶段或推荐有证据的下一检查。修复后的结果用于生成标签，但不能泄漏到当时的输入特征里。

标签包括：经验证的原因、有效修复规则、适用环境、反例，以及 unknown/尚未验证。业务失败不直接等于“坏操作”，回放 pass 不直接等于“正确根因”。LLM 可辅助生成标签提案，未经验证不升级为训练真值。

同一故障应构造“相似但不适用”的难负例：例如 HIDE 与 DESTROY、同 PID 不同顶层窗口、相同标题不同实例、轨迹缺陷与产品自身业务失败。负例由上下文决定：一份失败案例也可能是正确的参考，不能把所有失败录制一律当负样本。

### 11.2 学习目标与顺序

| 顺序 | 目标 | 建议方法 | 输出边界 |
|---|---|---|---|
| 先做 | 相似案例是否真正适用 | 对照样本与难负例；验证后可微调小型 reranker | 为历史证据排序，不产生动作授权 |
| 再评估 | 判断 capture/compile/replay/environment 等故障阶段 | 有拒判能力的监督分类；证据不足输出 unknown | 给出概率/证据，不能自行宣布根因 |
| 有稳定样本后 | 推荐下一检查或现有修复规则 | 审核后的结构化示范做 SFT；需要生成模型时可考虑 LoRA | 受限建议或规则 ID，不直接输出任意桌面动作 |
| 可选后期 | 同一上下文下优先推荐更正确、低风险的建议 | 经比较验证的 chosen/rejected 偏好对；必要时考虑 DPO | 优化建议偏好，不把成功/失败两条任意轨迹拼成偏好对 |

首选小型 reranker，而不是微调能控制桌面的通用 Agent：目标窄、标签可核查，且不会取代现有定位与执行门。LoRA 只是低成本微调手段，不是数据不足或标签错误的解决办法；初期也不从零训练模型。

### 11.3 优化必须在离线对照中证明

先固定未训练检索基线，再比较新增模型。按原录制/任务族/产品版本/时间隔离训练、开发和保留测试；同一次录制的裁剪、重录、修复前后版本不得跨集合泄漏。用于设计修复的题不能继续冒充未见测试。

比较适用案例排序、误推荐率、unknown 拒判、处理时延，以及最终经授权验证的修复收益。测试必须包含“看起来相似但不适用”的样本，不能只测已知正例。先用 shadow 模式旁路打分；不优于基线或增加错误建议就不启用。

### 11.4 发布不是实时自我改权重

新案例先候选入库，审核标签后周期性离线形成数据快照；训练产物记录数据/代码/基础模型/adapter 指纹及适用范围。经固定测试与审核后才切换推荐模型，保留旧版回退。样本量与多样性不足时继续用检索和规则，不预设“录够某个次数就自动训练”。

不在真实 EDR 桌面上做探索式强化学习，不用现场成功率奖励模型绕过断言，不自动扩大 GUI 权限。历史经验与学习模型始终只提供候选建议；当前观测、断言、租约和 unknown 阻断仍由既有执行链裁决。

参考（官方资料，方法依据而非已实施能力）：
- Sentence Transformers [CrossEncoder training](https://sbert.net/docs/cross_encoder/training_overview.html)：相关性训练与难负例。
- Hugging Face TRL [DPO Trainer](https://huggingface.co/docs/trl/main/dpo_trainer)：基于偏好数据的训练。
- Hugging Face PEFT [LoRA](https://huggingface.co/docs/peft/main/conceptual_guides/lora)：参数高效微调。

## 12. 有界强化学习：学习诊断策略，不在真实桌面随机探索

用户补充（2026-11-17）：可借鉴少量强化学习。本节仍是设计候选，不启动训练或在线实验；不把全部技术路线都列为首版必须实现。

### 12.1 首选上下文老虎机，而非端到端 GUI 强化学习

把一次决策限定为“在当前故障证据下，优先推荐哪项检查/哪条既有修复规则”。先使用 contextual bandit 学习建议排序：输入上下文，选择一项候选，记录该选择实际获得的反馈。它只学单次选择，不冒称已经解决多步规划和长期因果归因。

- 上下文：当前已知的故障阶段、诊断码、环境版本、输入来源、窗口生命周期、证据缺口、剩余预算。不能包含决策后才知道的结果。
- 候选：检索对照案例、核查已保存 down/up 归属、检查实例时间线、验证某条已有修复规则、提示需要人工补证或具体授权。必需采集/断言/授权门不是可选候选，不能学习跳过。
- 决策层仅返回建议。默认自动运行的候选只限已允许的本地只读检查；远端观测、GUI重录、修改程序或部署仍走原授权边界。
- 日志：decisionId、候选集合、实际选择、选择策略与版本、真实选择概率（若策略有随机性）、上下文摘要、结果证据、耗时/预算、反馈是否完整。

历史人工操作没有真实选择概率时保留 unknown，不事后伪造 propensity。未选择的检查没有真实收益标签，不能因为最后修好了就假设所有其他检查都无效。

### 12.2 奖励不能等同于“最后 pass”

安全与真实性是外部硬约束，不是可以用速度收益抵消的扣分项：删除/弱化断言、伪造观测、越权派发、unknown 重试等候选在选择前即排除。模型不能修改奖励计算器或验收器。

在合法候选中，分别记录并评估：

| 反馈 | 可记录的收益/成本 | 防止误学 |
|---|---|---|
| 有证据的检查 | 实际确认或排除具体假设 | 模型自称“信息增益高”不构成奖励 |
| 完整修复验证 | 未削弱原要求的新 run 与业务断言通过 | ready、receipt ok 或样本移出不是修复成功 |
| 效率 | 总耗时、额外采集次数、重复同故障次数 | 不以少录必要信息换取低时延 |
| 有效停止 | 发现缺授权、证据不足或 unknown 并正确阻断 | 不把停止算业务成功，也不能奖励无理由永远拒绝 |

先保留分项指标，不提前拍定加权常数。终局成功是延迟反馈，未验证贡献的中间检查不能都被标为正确根因。授权等待、运行中和缺失反馈分别记录，不能算失败或零收益后直接训练。

### 12.3 探索范围与离线评估

首版在保存的案例和可重现离线夹具中比较建议策略，先 shadow 旁路，不改变真实执行选择。存在足够多样性与反馈后，才考虑在低风险、本地只读候选中做受控探索；禁止在 EDR 桌面上随机点击或尝试业务操作来获取奖励。

离线评估必须检查历史策略的覆盖范围。IPS/DR 等方法需要正确的选择概率、足够支持和相应假设，不能凭确定性旧日志证明新策略在未尝试动作上有效。缺少条件时用固定离线任务、专家审核与受控验证，不宣称反事实收益已获证明。

策略版本按固定保留集比较错误建议率、正确拒判与有效进展、验证修复率及总耗时，报告样本数和不确定性；不是只比较训练奖励。收益不足则保留规则/检索基线，不发布新策略。

若未来积累了可复现的多步状态转移与可靠反馈，再评估保守离线 RL；现在不引入 PPO/GRPO/CQL 等完整训练栈，不新增一个项目来替代现有 recover。候选策略必须保持既有 JOB 总预算和 unknown 终止语义。
